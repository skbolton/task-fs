# Design

## Context

A greenfield Go program mounting Taskwarrior as FUSE. Grounding facts observed on the target system: Taskwarrior 3.4.2 with the TaskChampion SQLite backend, and `task status:pending export` emits one JSON object per task with stable `uuid`, `description`, `project`, `tags`, and `status` fields. `project:X` natively matches `X` and all dotted subprojects, and Taskwarrior reserves uppercase virtual tags (`+COMPLETED`, `+DUE`, `+OVERDUE`, ...) for derived metadata, erroring if a user adds them directly. See proposal.md for motivation and the spec deltas for required behavior.

## Goals / Non-Goals

**Goals:**

- Path-as-filter: every directory's listing is `task <path-filter> export`; the filter is accumulated during descent, never re-parsed from the path string.
- One naming rule for task files that stays stable as the database changes.
- All mutations flow through `task` CLI commands, so Taskwarrior remains the single source of truth and its own consistency rules apply.

**Non-Goals:**

- Any caching layer (added later at the single query boundary if polling load ever shows up).
- Reading `taskchampion.sqlite3` directly, or Go bindings to TaskChampion.
- Note editing (task files are read-only in v1; a future out-of-tree note system will make file edits map to task annotations), description rename via `mv`, `+DELETED` browsing, a "show all statuses" view (v2+ candidates).
- Enforcing or normalizing path order inside the mount. The canonical form (project segments first, then tags) is only the spelling used where the filesystem *emits* a path — docs, examples, any future scripting interface. Inside the mount, segments parse order-free (`/+next/home` and `/home/+next` resolve to the same node and filter), so any cd route works; the one cost is that two paths can spell the same state, which is accepted (see the order-free grammar decision for why symlink-based canonicalization was rejected).

## Decisions

**Go + go-fuse, shelling out to `task`, rather than Rust + taskchampion library.** The JSON export format is Taskwarrior's stable contract and survives Taskwarrior upgrades untouched; the taskchampion crate's API has been moving, and its performance advantage is irrelevant at personal task counts. Alternative considered (Rust direct-to-SQLite) is noted above as a contained v2 fallback if listing latency ever matters. go-fuse's `fs` API suits dynamic trees: an `Inode` per path node with `Lookup`, `Readdir`, and `Getattr` handlers.

**Order-free path grammar with prefix-based segment parsing.** A segment starting with `.+` and a fully-uppercase remainder is a virtual tag; a segment starting with `+` is a tag; anything else is a project segment. Virtual tags appear in listings as hidden dot entries (`.+COMPLETED`) so file managers and `ls` can toggle their visibility, and the dot form is the only spelling — a bare uppercase `+` segment resolves as an ordinary (case-sensitive) tag, never as a virtual tag. Dot-prefixed names are otherwise reserved: `mkdir` rejects them. No symlinks: symlink "teleporting" to a canonical node was considered and rejected because shells keep logical paths in `$PWD`, so canonicalization would not reach the prompt anyway. Canonical order (projects, then tags) is a serialization convention for anything the FS emits, not an enforced structure.

**Filter accumulation during descent, segment universe delegated to the CLI.** Each `Lookup` extends the parent directory's filter with the parsed segment. Each `Readdir` builds its entries from three `task` invocations against the accumulated filter: `_unique project` (full dotted names split into next-level child segments), `_unique tags` (comma-joined combinations split into individual tags — taskwarrior tags cannot contain commas, so the split is unambiguous), and `export` (task files: description, uuid). The virtual-tag universe is discovered once at mount time from `task _tags`, keeping the fully-uppercase entries; entries appear in listings as hidden dot entries with the fixed subset `COMPLETED`/`DELETED` carrying gesture semantics and `.+COMPLETED` mapping to `status:completed`. Delegating segment derivation means the FS reimplements none of taskwarrior's uniqueness semantics and absorbs virtual-tag additions across taskwarrior versions for free. Because virtual tags now carry their own `.+` spelling, a real uppercase user tag (`+NEXT`) is no longer shadowed by virtual tags — it resolves as an ordinary tag. Fallback if fork overhead ever matters: derive segments from the single `export` result set instead, or add the short-TTL cache. The "known segments" set comes from these results plus explicit `mkdir` declarations, which makes typo'd lookups fail ENOENT instead of showing empty directories. Project segments join with `.` when accumulated; tags and virtual tags translate directly (`+next` -> `+next`, `+DUE` -> `+DUE`, `+COMPLETED` -> `status:completed`).

**Flat task files named `<description>.<first-8-hex>.md`, content = empty, read-only in v1.** A task file appears exactly once in the project tree: in the directory whose accumulated project filter equals the task's exact project, so subproject tasks do not leak into ancestor directories (the tree navigates hierarchically, but listing is exact). Directories whose filter has no project segment (root, tag views, virtual-tag views) list every matching task. The uniform short-UUID suffix is the first segment of the task's UUID; it keeps names stable as the database changes. Kernel inode identity is per-view (hash of the view's filter plus the UUID), not global: the same task legitimately appears in overlapping views (e.g. `/home` and `/home/+next`), and a global inode number makes `mv` refuse the move as "same file" before the filesystem can apply the tag delta — the exact-project-and-drop-a-tag gesture. The `.md` extension carries the human-facing connotation and is deliberate groundwork: a future out-of-tree note system will make the task file itself the note, so that editing the file edits the task's annotations (taskwarrior's quick-note style) — v1 ships the file as a blank read-only placeholder and rejects writes rather than silently discarding them, keeping the write path reserved for that design. Task identity is carried as the `user.taskwarrior.uuid` extended attribute on every file, and every mutation gesture resolves the inode to that full UUID before invoking `task` — the suffix, the extension, and any visible identifier are display-only. A spike against TW 3.4.2 confirmed why this hardening matters: bare hex arguments below 8 chars silently match nothing, `uuid:<prefix>` filters match *all* prefixes (so a mutation command with an ambiguous prefix bulk-applies with exit 0 and no prompt), and `task _get <prefix>.uuid` silently returns the first match on ambiguity. Integer task IDs were considered as the suffix (familiar from `task list`) and rejected: they exist only for pending tasks (`id: 0` on completed exports) and are silently renumbered by the garbage collector on every add/delete, so names would churn without any user action. Descriptions are sanitized deterministically to the character set legal on both Linux and Windows (banning the Windows-illegal set `\ / : * ? " < > |`, handling reserved device names and trailing dots/spaces) so a future Windows port never needs to re-migrate names; truncation to the 255-byte name limit always retains the suffix and extension. Directory-per-task was considered and rejected: the flat form keeps `ls` equal to the task count, and with notes living in the file content there is no longer any need for a per-task directory.

**Gestures:** `touch "Description"` -> `task add proj:<dir project> <dir tags> "Description"`, with the write filter derived by dropping virtual-tag segments from the current filter — the read/write split Taskwarrior contexts have, derived from location instead of maintained by hand. Consequence: a task created under a read-tightened view (e.g. `/home/.+DUE`) does not match the filter and its file vanishes from that directory, appearing one level up — identical to adding under a Taskwarrior context, so accepted as the known cost. `rm` -> `task <uuid> delete`; all other moves unify under one delta rule — **after the move, the task's project and tags match the destination directory's filter** (delta computed between source and destination filters; moving to a parent project sets the project exactly, dropping the subproject; moving out of a tag directory drops that tag). Status moves stay special-cased: moving into `.+COMPLETED` completes and ignores the rest of the destination path; moving out reopens and additionally applies the destination delta. `mkdir` declares a filter segment (tag or brand-new project) that no task matches — in-memory for the mount session; dot-prefixed and virtual-tag names rejected, EEXIST on redeclare, ENOTEMPTY on rmdir of a tag in use. Renaming a task file (description change) is rejected in v1. Symlink-based tag assignment (`ln -s <tag> <taskfile>`) was considered and rejected: the link name collides with the existing task file (EEXIST), and symlink membership markers conflict with the order-free node model, where the same node is reached via both project-prefixed and tag-prefixed paths and cannot be both "the file" and "the marker." The taskwarrior CLI remains the fallback for anything the gestures do not cover.

**Touch detection.** A `create` of an empty file is treated as task creation with the file name as the description; names minted by the filesystem always end in `.<8-hex>.md`, so a create matching that pattern is rejected, protecting the invariant that only the FS mints those names.

**Move interception.** The kernel resolves a rename's parent chain through `Lookup` (which stays intent-blind and therefore strict: no auto-vivification, preserving typo-ENOENT), then hands the rename itself to the FS's `Rename` handler with the final component as a plain name that need not exist. The handler interprets that component: a task-file-looking name would be a description rename (rejected in v1), `+tag` is a tag delta, anything else is a project segment minted on demand. GNU mv stats the destination first and appends the source basename when it is an existing directory, so both `mv X <existing-dir>/` and `mv X <existing-dir>` arrive as into-directory moves; for a nonexistent final component only the no-trailing-slash form reaches `Rename` (the trailing-slash form fails ENOENT at lookup, standard POSIX behavior — documented, not worked around).

**Mount lifecycle.** `task-fs mount <mountpoint>` runs the mount in the foreground (Ctrl-C unmounts cleanly); backgrounding/daemonizing is left to the user's session manager. The process never resolves the database location itself: `task` inherits the environment (`TASKDATA`, `rc.data.location`), so alternate databases work without any task-fs flag. A missing `task` binary fails the mount at startup.

## Risks / Trade-offs

- [FUSE polling clients (file managers) re-query directories periodically] → Each readdir is three `task` forks (`_unique project`, `_unique tags`, `export`, ~tens of ms total at personal task counts). Accepted for v1; if it matters, derive segments from the single export result set or add a short-TTL cache at the query function boundary.
- [Identical names (same description, same 8-hex prefix) shadow one another in a listing] → Accepted by design; probability at personal task counts is negligible, gestures still resolve by full UUID so nothing breaks functionally, and the user resolves the ambiguity in Taskwarrior itself.
- [Uppercase user tags were shadowed by virtual-tag segments] → Resolved by the hidden-entry spelling: virtual tags are `.+NAME`, so an uppercase user tag `+NAME` resolves as an ordinary tag.
- [Project names containing `.` or empty segments] → Taskwarrior splits projects on `.`; the FS never reconstructs projects from paths (filters accumulate during descent), so ambiguity is avoided by construction. Any future path-argument interface must document that dotted segments are unambiguous only via the accumulated filter.
- [Tag/segment declarations are in-memory only] → A `mkdir`-declared segment with no tasks matching it lives in daemon memory and disappears on unmount; acceptable because the declaration only bridges mkdir to mv, after which the directory exists naturally from query results. A state file is the fallback if this annoys.
- [Delta-rule mv silently drops attributes by design] → Moving to a parent project sets the project exactly (subproject dropped) and moving out of a tag directory drops that tag; the declarative principle is "the task matches where you put it" — the path is the complete specification. Documented loudly rather than guarded.
- [Taskwarrior CLI output format changes] → All queries parse `task export` JSON, the tool's documented stable interface; version-checked at startup with a clear error if absent.
- [Windows support door] → Names are already Windows-legal by construction; the actual port blocker is go-fuse lacking a Windows backend (future route: WinFsp). No commitment made in v1.
- [macOS expected to work but untested] → go-fuse supports darwin and the spec grammar is platform-neutral; the host requirement is the macFUSE system extension (user-approved, reboot-prone), which is why Linux is the only v1-tested platform. Known macOS wrinkle when someone actually mounts on Apple hardware: APFS normalizes filenames to NFD unicode, so lookup equality must not assume byte-identical description round-trips; a NixOS `aarch64-darwin` build target keeps this honest.

### Spike evidence (TW 3.4.2, verified against live CLI)

- `task <bare-hex>` requires >= 8 chars; shorter silently matches nothing.
- `task uuid:<prefix>` is true prefix matching with no minimum; an ambiguous prefix combined with a mutation command (`task uuid:<prefix> done`) applied to *all* matches with exit 0 and no prompt.
- `task _get <8hex>.uuid` expands a prefix to a full UUID but errors below 8 chars ("not a DOM reference") and silently returns the first match when the prefix is ambiguous.
- Completed/deleted tasks export `id: 0`; integer IDs are unique only among pending tasks and are renumbered by the garbage collector on every add/delete.
- No dedicated short-UUID API exists; shortening is this filesystem's own display convention.

## Migration Plan

New system, nothing to migrate. Rollback is `fusermount3 -u <mountpoint>`; the database is only ever touched through `task` commands, so unmounting leaves no residue.

## Open Questions

None blocking. Cache TTL policy and daemonization are deferred until real usage shows a need; note editing is scoped to v2.
